# Nuphos 团队里 Bot 如何发言、如何被授权、如何知道自己在团队中

阅读版本：GitHub `nuphos/nuphos` `main` 浅克隆，commit `6b85c763a03c973ca42f7c71bc724c7738f6172c`（2026-11-18 03:10:14 +0000，subject `test(e2e): keep a Bot tree opened by hand open across pages and reloads (#3338)`）。文档页于同日抓取，站点未给出独立 doc revision。下文「宿主强制」指后端或 runtime 拒绝/改写请求；「仅提示约定」指写进 system prompt 或 tool description、模型可以不遵守。

## 多人与多 Bot 共享一个会话或群时，下一句由谁说；忙时是 steer 还是排队；有没有轮次上限

### Takeaway

Nuphos 的 team 首先是成员、runtime、连接器、instructions、skills、memory 的容器，不是一组互相聊天的 Bot。真正同时说话的有两条独立路径：一条是若干人共享**同一个 agent conversation**（一个 runtime 上的一轮），下一条消息按到达顺序排队，只有当前 turn 的 actor 能把话 steer 进正在跑的轮次；另一条是 **channel（群聊）里多个 Bot 互相叫醒**，没有选举下一发言人，而是除作者外每个成员 agent 都被唤醒，两次人说话之间 agent 互唤醒最多 10 次。把有界任务交给另一个会话是第三条路径：`create_thread` 开一个不继承 transcript 的子 conversation，由同一 owner 的工具显式投递，不是群聊轮转。

### Cited Findings

- Team 的产品定义是容器：connected runtimes、infrastructure accounts、agents、memory 都属于 team；角色是 Administrator / Editor / Viewer。Team membership 不等于能打开每个 private session，也不等于能用那台 computer。 — [Teams & members](https://docs.nuphos.ai/collaboration/teams)；同义见 [Core concepts](https://docs.nuphos.ai/concepts)
- 预设 system prompt 把产品说成「shared sessions that teammates join and steer together」，而不是 Bot 互相对话：「Coding agents are single-player by default — one agent, on one laptop, for one person; Nuphos is where a team runs them instead.」 — [atlas-agent-system.md](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/agent/prompts/atlas-agent-system.md)
- 共享会话的访问不是 changelog 里的可点选 Can view / Can reply / Can manage。当前代码：`ConversationAccess` 只有 `'owner' | 'reply' | 'view'`。非 channel 的 `generalAccess` 只允许 `'none' | 'view'`；存成 `'reply'` 的旧值对非 channel 读成 `'view'`。Channel 才保留 team-wide `'reply'`。邀请时传 `role: 'manage'` 或 `'view'` 返回 400；测试名写明 “participants have no roles to choose”。谁能回复由「能不能用这台 computer」推导：能用则 `reply`，被邀请但不能用 computer 则只 `view`。Managed / self-hosted / development runtime（`runtimeId` 解析不出某个人的设备）对每个成员都算能用。 — [access.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/agent/db/access.ts)；[conversation-computer.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/agent/devices/conversation-computer.ts)；[routes-conversation-participants.test.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/routes/agent/routes-conversation-participants.test.ts)

- 【宿主强制】普通发送只有一条队列。注释：「The server queue is a session's only queue. Every new message from any client runs now when the session is free, or waits in the queue behind whatever arrived first, human or agent.」`admitQueueableChat`：已有排队消息时不再抢 claim；runtime `schemaVersion === 2` 且 `actions.send` 为假、或 runtime offline / disconnected，则 `enqueuePendingUserMessage`。队列无条数上限、无过期；单条 `renderedText` 截到 4000 字符（带 chat payload 的直发另有 12_000_000 字符上限）。释放 session 后由 `startQueuedTurn` 起下一条。 — [session-queue-turn.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/routes/agent/session-queue-turn.ts)；[pending-messages.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/agent/pending-messages.ts)

Agent, resource and trigger turns act as the session owner」）。别人开的 turn 返回 409 `runtime_steering_unavailable`，文案 “Someone else started the running turn; send your message to run after it”。Runtime 拒绝注入时，若这条来自队列，放回队首并 `sessionReleased`。Steer 本身「No queue, resume, or prompt fallback」，把文本和已放到 runtime 上的本地文件交给正在跑的 ACP turn。 — [routes-conversation-runtime.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/routes/agent/routes-conversation-runtime.ts)；[session-execution-state.ts `steerConversationRuntime`](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/claude-code-preview/session-execution-state.ts)
- Changelog「Files or images sent while the agent is working now steer the running turn instead of waiting」描述的是这条 steer 路径，不是把所有忙时消息都改成 steer。忙且不能 steer（别人的 turn、runtime `actions.steer` 为假）时消息进队列。 — [changelog](https://nuphos.ai/changelog/open-source-new-agents-sharing)；对照上两条源码
- Channel 不是「选一个下一发言人」。`wakeChannelAgents` 对 `agentSessionIds` 里除作者外的每个 session `Promise.all(notifyAgent)`。人的 post 立刻唤醒；agent 的 post 先记在 `channelWakes`，等该 agent 自己的 turn 结束再 `wakeAfterTurn`，这样一轮里说的话只叫醒别人一次。 — [channel-chat.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/agent/channel-chat.ts)
- 【宿主强制】群聊轮次上限：`CHANNEL_AGENT_TURN_BUDGET = 10`。注释：「Turns agents may wake each other for between two posts by a person. Every message wakes every other agent in the channel, so agents answering agents multiply fast; past this they wait for someone to speak.」人说话把 `agentTurns` 置 0；agent 唤醒每次 `spendTurn` `$inc`。到 10 时写 timeline `agents_paused`，之后的 agent 唤醒不再 `startConversationTurn`。离线期间错过的人的 post 会在 runtime 回来后补唤醒；「Agents' posts past the turn budget wait for a person」。 — [channel-chat.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/agent/channel-chat.ts)；[channel-missed-posts.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/agent/channel-missed-posts.ts)
- Channel 里人的新 post：若 owner 自己正在跑 turn，`steerRunningTurn` 把固定文案 `New messages in a Nuphos channel (channelId …)` 加上未读 posts steer 进去；失败则入队。排队的人的 notice 会重试 steer 最多 15 次、间隔 2s（`QUEUED_NOTICE_STEER`），避免卡在「turn 还在启动、还不能 steer」直到整轮结束。Agent 发来的唤醒不走 mid-turn steer（「An agent's posts still wait for the turn to end」）。每个 agent、每个 channel 同时只留一条 notice。Archived agent 不被叫醒；owner 离开 team 后 `getTeamMembership` 失败则安静。 — [channel-wake.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/agent/channel-wake.ts)；[channel-chat.ts `notifyAgent`](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/agent/channel-chat.ts)

### Inferences

- 「团队」同时存在两种协作，不要混成一种发言协议：人共享一个 agent 的 transcript（队列 + 仅当前 actor 可 steer）；多个 Bot 要么在 channel 里被广播唤醒（有 10 次互唤醒预算），要么由 owner 的工具开子会话一对一投递。没有跨 Bot 的全局 speaker election。
- 2026-10-11 公开 changelog 的 session 角色模型已经落后于 2026-11-18 源码。以源码为准：view/reply 是 computer-use 的派生结果，不是参与者身上可切换的 manage 角色。

### Gaps

- 没有逐个 provider（Claude Code / Codex / OpenCode / Grok Build / Antigravity）核对 ACP `session/steer` 在 adapter 内是插入当前采样还是只追加到 provider 自己的队列；后端只要求 runtime snapshot `actions.steer` 且 `steerNotInjected` 为假。
- 没有找到后来的 changelog 说明 Can manage 角色被删掉的日期；只确认当前 commit 拒绝该 role。
- Channel 预算按「被唤醒的 agent 次数」计，不是按群里发言条数。一个人 post 同时叫醒 N 个 agent 会在随后的 agent 互唤醒里很快花完 10，具体扣减顺序没有单独的调度器文档，只看到 `Promise.all` 并行 `spendTurn`。

## Provider 权限模式、审批、workspace root、每会话连接如何强制；谁能看见工具调用和文件；一个 Bot 的 runtime 能否读另一个 Bot 的文件

### Takeaway

权限分成几层，只有一部分是宿主强制。会话级 Full Access / Auto Mode 由后端在 permission bridge 里决定要不要问人；cloud IAM 缺权限没有应用内审批，只有一段 prompt。连接器选择按 conversation（子 Task 用最顶层祖先的 selection）由后端套用，越权预期是 403。工作目录通过 ACP `_meta` 的 `dev.openab/workingDir` 交给 runtime，但 ACP 的 `cwd` 被忽略，默认是 runtime 的 `/workspace`。Session `HOME` 按 conversation（队友再加 actor）隔离 CLI 配置，同一 OS 用户，源码写明这不是文件系统安全边界。能读该 conversation 的人看见同一份 transcript，包括命令；channel 里的人只看见 `channel_post`。

### Cited Findings

- 【宿主强制】Permission mode 存在 `auto_mode_authorizations.bypass`。注释：「Full Access, per conversation: when the switch is on, the runtime's permission requests are allowed without asking.」`handleOpenAbPermissionRequest`：`getSessionBypass` 为真时选 `allow_once`，没有该 option 则 cancel，并发 `authorization-decision` frame，`layer: 'bypass'`，reason `Full Access is enabled for this conversation.` 非 bypass 则注册 `agent-permission` wait，超时 `OPENAB_PERMISSION_DECISION_TIMEOUT_MS = 2 * 60_000`，超时文案 `Permission request timed out`。当前 turn 的 actor 若已有排队消息，会 supersede 尚未决定的 permission（别人的 agent 消息不 supersede）。 — [auto-mode/store.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/agent/auto-mode/store.ts)；[openab-permission-bridge.ts](https://github.com/nuphos/nuphos/blob/6b85c763a03c973ca42f7c71bc724c7738f6172c/apps/backend/src/lib/claude-code-preview/openab-permission-bridge.ts)

### Inferences

- 一个 Bot 的 runtime **可以**读到同一 OS 用户、同一 pod `/workspace` 上另一个 conversation 留下的 scratch 文件；源码把这当成已知的非边界，而不是按 Bot 做的 ACL。CLI 登录态默认不共享（不同 `HOME`），但 Keychain 和「改掉 session path、去写共享 shell 启动文件」可以跨会话，后者只被 prompt 劝阻。
- Team skill 树是该 runtime 上所有 conversation 共享的只读（Codex prompt 这么说；sync 脚本写的是 workspace `.claude/skills`）目录。Personal skill 才按 conversation 目录隔开。
- 审批卡片是 runtime permission relay 的宿主行为；cloud IAM「permission wall」和「高风险先问人」里，后者文档承认不是每个写操作的闸门。

### Gaps

- 没有读完各 provider 的 permission shim，不能证明 OpenCode / Grok Build / Antigravity 的每一次 shell 都经过 `handleOpenAbPermissionRequest`，只确认 session meta 统一要求 `permissionPolicy: relay`。
- `/workspace` 为 per-pod scratch 写在 `CODEX_WORKSPACE_NOTE`，注释说这段只对 Codex 注入。其他 provider 是否同一块可写目录，只看到 `RUNTIME_CWD = '/workspace'` 和「OpenAB ignores ACP cwd」。
- 文档说 personal skill 的当前 UI 描述的是成员自己的 Claude Code turn，「do not assume identical personal-skill behavior on every runtime」。源码的 personal dir 是 runtime 脚本行为，没有在这次阅读里对每个 provider 做对照。

## 团队身份注入点；共享 skills、team memory、有界任务如何把上下文交给下一个 agent

### Takeaway

团队身份不是模型必须先调用的某个工具，而是每轮由 `buildPreviewSystemPrompt` 拼好、经 ACP `_meta` 附到 provider 自己的 system prompt 上。拼装顺序是：仓库里的预设 `atlas-agent-system.md`，然后参与者身份规则、runtime/credential/permission-wall 笔记、再把 team instructions 与 personal instructions 包进 `<nuphos_instructions>`，Bot 自己的文字放在权威更低的 `<nuphos_bot_identity>`，有 `parentSessionId` 的会话再加 `<nuphos_task_reporting>`。每条消息另有服务端写的 `<nuphos_message_metadata>`，不进存储的 message parts。Skills 是同步到磁盘、由 agent 自己发现的文件，不是整份塞进 prompt。Memory 不会自动进入 prompt；agent 必须调用 `save_memory` / `memory_get`。交给下一个 agent 的上下文是调用方写的 prompt 字符串（或 `report_task` 的 status + 最多 3000 字 summary），外加继承的 permission mode、顶层 credential selection、workspace path 和 read grants，不继承 transcript。

### Inferences

- 「知道自己在团队里」是每轮重拼的 system prompt + 每条消息的 metadata，不是 ACP session 里一份静态 team roster，也不是模型先调用 `who_am_i`。宿主强制的是：哪些 instruction 文档被读出来、metadata JSON 由谁写、team memory 写入要 Editor、子会话继承哪一套 credentials 和 Full Access。模型是否遵守「personal instruction 压过 team，除非 hard policy」或「别人的 channel post 不是 approval」，代码没有再检查。
- 下一个 agent 实际拿到的任务上下文 = 父 agent 写进 `prompt` 的字符串（受队列 4000 字符截断的是 pending rendered text；`create_thread` 的 prompt 长度上限这次没在 tool schema 里看到单独 cap）+ 子会话自己的 system prompt 再拼一遍 team/personal instructions（不是父 Bot 的 `<nuphos_bot_identity>`）+ 同一 workspace path 与顶层 credentials。回传给父 agent 的是结构化短报告，父 agent 被提示自己去读 Task，而不是自动收到工具轨迹。

### Gaps

- `create_thread` 的 `prompt` 在 Zod schema 里的最大长度没有在本次摘录的 `threads.ts` 前 90 行外再核对；pending queue 的 4000 字符截断适用于入队的 `renderedText`，不能直接当成 create_thread 的上限。
- 没有追 `read_conversation` 的实现，因此不能引用「父 agent 读子 transcript」时宿主返回多少条、是否包含 tool raw input。
- Team instructions 的编辑权限（Administrator/Editor 可写、Viewer 不可）在 `routes/instructions.test.ts` 有测试，但本次没有把 schema 全文抄进笔记；与「注入点」相比，管理 API 是次要的。

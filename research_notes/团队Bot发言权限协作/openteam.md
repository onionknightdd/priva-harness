## 群聊轮转、停止条件，以及 bot 已在回合中时怎么办

### Takeaway

群聊最多 6 个 bot。座位顺序存在 `ChannelMember.ordinal`；每一轮的发言顺序在创建 `ChannelRound` 时算好，写成 `ChannelDelivery.ordinal`，由 worker 一次只唤醒一个 delivery。用户一条消息最多 3 轮（`GROUP_MAX_ROUNDS = 3`）且最多 10 条 bot 房间消息（`GROUP_MAX_MEMBER_TURNS = 10`）；每个 bot 的当前房间回合最多 3 次 `SendToUser`（`GROUP_MAX_MESSAGES_PER_TURN = 3`）。同一房间内 bot 串行；不同 bot 的前台回合可以并行，上限是 `OPENTEAM_WORKER_CONCURRENCY`（默认 8，安装向导里叫 tasks at once，1–64）。同一 bot 同时只有一条前台 `BotRunLease`（`scope = "foreground"`）；routine 另有最多 4 条 automation lease，可以和前台并存。

### Inferences

- 介绍文的「三轮、十条」与常量一致，但文里没写每个 bot 回合另外还有 3 条 `SendToUser` 的宿主上限。
- 「one turn at a time per bot」在代码里是一条前台 lease，不是该 bot 的全部执行：最多 4 个 routine 可以与前台同时跑。群内顺序比这更严，是一轮里一个 delivery。
- 轮转存在数据库的 delivery 序里，不是只写在 prompt 里。prompt 告诉模型「现在轮到你」以及可以沉默；谁被唤醒、何时停，由 `advanceRound` 决定。

### Gaps

- 没有在运行中的服务器上复现一轮群聊，结论来自该提交的源码与测试名所指向的行为。
- `priority_peer_interrupt` 的群重投路径存在，但按 `PRIORITY_INTERRUPTIBLE_ORIGINS`，正在进行的 group 前台 run 不应被优先级私信打断。重投更可能来自用户消息取消路径与该错误码的交叉，或来自恢复逻辑；本笔记没有把每一条调用链跑完。

## wake 如何领取回合，以及送进 Pi 的是什么

### Takeaway

一次 wake 先落成 `Message` + `Run` + `InboxEvent`，再向 pg-boss 队列 `bot-wake` 投 `{ botId }`。worker 的 `claim` 在 bot 级 advisory lock 里把一条 inbox 标成 `processing`，写下 `BotRunLease`，把 run 标成 `running`。群回合的正文是 `buildGroupTurnPrompt` 生成的纯文本，`wrapUserContent: false`，因此不会再包 `<user_query>`。worker 把这段字符串放进 `ComputerTurnRequest.content`，`instructions` 是平台 system prompt。computer 用 Pi 的 `systemPrompt: instructions`，再 `session.prompt(content)`，也就是模型看到的 user 消息。发言顺序由谁被 enqueue 决定，不是由 prompt 建议模型按顺序说话。

### Cited Findings

- `enqueueWake`：bot 须为 `active`（`user`/`agent` origin 也允许 `provisioning`）。写入 role 为 `user` 的 `Message`（bootstrap 除外，role 为 `system`）、`Run`、`InboxEvent`，然后 `boss.send("bot-wake", { botId })`。`wrapUserContent !== false` 且 origin 不是 bootstrap 时，正文被包成 `<timestamp>...</timestamp>\n<user_query>\n${content}\n</user_query>`。群回合调用处显式 `wrapUserContent: false`、`origin: "group"`、`type: "group.message"`、`priority: PRIORITY.group`（150）。 — [index.ts `enqueueWake` / `advanceRound`](https://github.com/raghavpillai/openteam/blob/3c7cb2297e6175a49c2aa725030422b1d316f7d9/packages/messaging/src/index.ts)、[timestamps.ts](https://github.com/raghavpillai/openteam/blob/3c7cb2297e6175a49c2aa725030422b1d316f7d9/packages/messaging/src/timestamps.ts)
- 群回合 user 文本以 `[Group chat: ${JSON.stringify(群名)} - with 同伴名]` 开头，可含 `Room:`、`Participants:`（同伴的 description），然后 `New messages in the room (oldest first):` 与 `Name: ...` 行。固定收束句：`It's your turn, ${targetName}. Reply in character with SendToUser if you have something worth adding; if you don't, end your turn without sending anything.` — [buildGroupTurnPrompt](https://github.com/raghavpillai/openteam/blob/3c7cb2297e6175a49c2aa725030422b1d316f7d9/packages/messaging/src/index.ts)
- context：`contextScopeForRun`。`routine` 用 `scope: "automation"`，scopeId 为该 routine run。其他 origin 在有 `channelId` 时用 `scope: "channel"`、scopeId 为频道 id，否则 `scope: "home"`、scopeId 为 conversation id。因此同一个 bot 的 1:1 与每个群各有一份 Pi session（`ContextSession.runtimeSessionPath`）。 — [worker.ts `contextScopeForRun`](https://github.com/raghavpillai/openteam/blob/3c7cb2297e6175a49c2aa725030422b1d316f7d9/apps/worker/src/worker.ts)
- `execute` 组装 `ComputerTurnRequest`：`content` 为 wake 正文（可再前置 automation / profile / instructions 笔记），`instructions` 为 `platformPrompt.instructions`，`userInfo` 为 `<user_info>` 块，`cwd` 为 workspace root，`requestSource` 对 group origin 是 `"agent"`（`runtimeRequestSourceForOrigin`）。POST 到 computer 的 turns 路径。 — [worker.ts `execute`](https://github.com/raghavpillai/openteam/blob/3c7cb2297e6175a49c2aa725030422b1d316f7d9/apps/worker/src/worker.ts)
- Pi：`createStandaloneSession` 把 `instructions` 设为 `DefaultResourceLoader` 的 `systemPrompt`（再经 `taskProgressBaseInstructions`）。`execute` 调用 `session.prompt(content, { source: "rpc", images })`。`userInfo` 被钉进 session，成为带 `providerOptions.cursor.isUserInfo` 的 user 消息，并在压缩时保持在历史前面；它不是本回合的 `content`。ambient / 未送达的更早用户输入走 `prependMessages`，以 custom message 写入且 `triggerTurn: false`。 — [runtime.ts](https://github.com/raghavpillai/openteam/blob/3c7cb2297e6175a49c2aa725030422b1d316f7d9/apps/computer/src/runtime.ts)、[compaction/messages.ts `replaceBotUserInfo`](https://github.com/raghavpillai/openteam/blob/3c7cb2297e6175a49c2aa725030422b1d316f7d9/apps/computer/src/compaction/messages.ts)
- 托管 skill 的触发说明写明：user 消息以 `[Group chat: "…"]` 开头才是房间回合。skill 正文要求用 `SendToUser` 对房间说话，纯 assistant 文本房间看不见；`to:"dm"` 才进自己的 1:1。这与宿主一致：房间回合里 `SendToUser` 且 `to !== "dm"` 只接受 `type: "text"`，并进入该 delivery 的 outbox。 — [managed-skills.json `group-chat-turns`](https://github.com/raghavpillai/openteam/blob/3c7cb2297e6175a49c2aa725030422b1d316f7d9/packages/messaging/src/prompts/managed-skills.json)、[sendVisible](https://github.com/raghavpillai/openteam/blob/3c7cb2297e6175a49c2aa725030422b1d316f7d9/packages/messaging/src/index.ts)
- 介绍文对链路的叙述（server 存消息并排队 wake，worker claim，computer 里的 Pi 调模型）与上述代码同向。 — [introducing-openteam](https://openteam.so/blog/introducing-openteam)

### Inferences

- 模型不能靠「在错误的时机调用 SendToUser」插队：没有 active group delivery 时，群里的 `SendToUser` 会自己 `createGroupRound` 并排除发送者（`initiatorBotId`），那是新开一轮，不是抢当前轮的 ordinal。进行中的房间回合则把文本扣进 outbox，别人要等本回合结算才看得到。
- 群回合的 Pi user 消息就是调度器写的房间快照，不是用户原话的逐字转发。用户原话出现在快照的 `User:` 行里。

### Gaps

- 没有抓一条真实 Pi HTTP 请求体；`content` 与 `instructions` 的对应关系来自 worker 构造 `ComputerTurnRequest` 与 computer `session.prompt` / `systemPrompt` 的代码路径。
- `taskProgressBaseInstructions` 是否改写群回合 system prompt 的具体差分未逐行展开。

## 文件系统、桌面与共享 /workspace

### Takeaway

所有 bot 的桌面跑在同一个 computer 容器里，上限 100 个 live screen。每个 bot 有自己的 X display、VNC 端口和 Chromium `--user-data-dir`，但进程用户是同一个 `box`（uid 默认 1000），`HOME=/home/box`。`/workspace` 是 0755、全体可读写的共享目录。浏览器登录通过进程内 cookie 协调和 profile 快照在 bot 之间复制，不是每人一份不可读的 profile。没有按 bot 划分的 Unix 沙箱：`sudo` 为 `NOPASSWD: ALL`，入口脚本写明 file ownership 不是隔离边界。记忆不在 bot 能读的计算机文件里，而在 PostgreSQL；群回合不注入、也不让该回合改写共享 user memory。bot A 用 Shell 可以读 bot B 的 home 与 agent 目录；`ReadTranscript` 在宿主上允许读取其他活跃 bot 的可见频道消息，但默认不附带对方的工具参数。

### Cited Findings

- 介绍文：每 bot 一块持久 XFCE 桌面，默认 1280×800，带 Chromium、文件管理器和终端；一个容器最多 100 个。全体共享 `/workspace`。浏览器登录也共享：在任一 bot 的屏幕登录后，每个 bot 都已登录。 — [introducing-openteam](https://openteam.so/blog/introducing-openteam)
- 文档：每 bot 自己的屏幕，故多个 bot 可以同时用浏览器；共享 `/workspace` 和网站登录。computer 容器与用户自己的电脑分开。 — [architecture](https://openteam.so/docs/overview/architecture)、[files](https://openteam.so/docs/usage/files)
- `MAX_SCREENS = 100`，分辨率常量 1280×800。display = `100 + slot`，RFB `5900 + slot`，viewer `6200 + slot`，浏览器调试端口 `9300 + slot`。profile 目录：slot 0 为 `/home/box/chrome-profile`，否则 `/home/box/chrome-profile-${slot+1}`。运行时目录 `/tmp/openteam-screen-${slot}`。Chromium 参数含 `--user-data-dir=${session.profileDirectory}`。 — [screen-broker.ts](https://github.com/raghavpillai/openteam/blob/3c7cb2297e6175a49c2aa725030422b1d316f7d9/apps/computer/src/screen-broker.ts)

- 没有在容器里用两个 bot 实际 `cat` 对方的 session 文件；入口脚本和同一 uid 已经说明不存在权限墙。

## bot 如何得知自己在一个团队里

### Takeaway

身份句只有 `You are OpenTeam, a warm, concise desktop assistant.` 团队关系不靠改写这句话，而靠每回合拼进 system prompt 的 `## Teammates and groups`、`A2A_PLATFORM_INSTRUCTIONS`，以及钉在对话前部的 `<user_info>` 里的 `<teammates>` 花名册。工具 `SendToAgent`、`CreateAgent`、`CreateChannel` 的 schema 是模型可见的合同。群回合另外在 user 消息里点名房间和同伴。skill `group-chat-turns` 在目录里，要模型自己去读。

## 子代理与 bot 对 bot 私信：上下文怎么传，收件人会不会自动开新回合

### Takeaway

`SendToAgent` 对另一个 bot 会立刻 `enqueueWake`，origin `agent`，正文是 `directAgentWake` 包出来的 `[agent]` 提示。收件人因此得到一次新的前台 wake；若当时前台正忙于 user / group / agent 回合，这条 wake 排队，不打断。`priority: true` 只打断 event、background_revival、broadcast。`Task` 创建一个隐藏的 child bot，并立刻 `enqueueWake` 把 `input.prompt` 当作它的第一条 user 消息；父回合不等待回复。`MessageSubagent` 再 enqueue 一条更高优先级的 steer，并打断子代理当前 run。子代理不能再 `Task`。

### Cited Findings

- 1:1 私信：`sendToAgent` 在找不到 group 时查找 target bot。拒绝发给自己、发给子代理、发给非 active/provisioning。把文本夹到 8000 字符，写入双方可见的投影，然后 `enqueueWake`，`origin: "agent"`，`type: "agent.message"`，`priority` 为 `PRIORITY.agent`（200）或 `urgentAgent`（250）。正文来自 `directAgentWake`：`[SAND_HIDDEN_PROMPT][agent] A message just arrived from another of your user's agents: ${name} (id: ${id}).` 接着说明这不是用户在打字、回复要用 `SendToAgent`、对方在稍后的新回合才收到、FYI 可以沉默。`wrapUserContent` 未设为 false，因此外层还有 `<timestamp>` 和 `<user_query>`。工具回执写明异步：`This is asynchronous — if they reply, it'll arrive later as a new message that wakes you`。 — [index.ts `sendToAgent` / `directAgentWake` / `directAgentAcknowledgement`](https://github.com/raghavpillai/openteam/blob/3c7cb2297e6175a49c2aa725030422b1d316f7d9/packages/messaging/src/index.ts)

### Inferences

- 「对方会不会自动获得新回合」：会。1:1 `SendToAgent` 和 `Task` 都在同一事务里 `enqueueWake`，pg-boss 随事务投出 `bot-wake`。自动的是一次新的模型回合，不是把父 session 接过来。
- 父传给子代理的上下文默认只有 `prompt` 字段（加 computerUse 站点笔记、时间戳包装、system prompt 里的 worker 专用节）。更早的父对话不会被复制进 child session。

### Gaps

- `assertSubagentCapacity` 的具体并发上限数字没有在本笔记里摘出。
- child 的 system prompt 与主 bot 的差异只确认了 automation 省略节、worker box 节和 `ReadTranscript` 拒绝；没有导出一份完整的子代理 `instructions`。
